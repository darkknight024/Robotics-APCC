This document explains **every plot (and the CSV/JSON that travels with it)**
written by the two diagnostic entry points:

| Entry point | What it is |
|---|---|
| `python tests/test_optimal_velocity_profile.py --dataset …` | Feature-3 Deliverable 2 velocity-profile run. Writes lettered groups `A_`…`T_` plus toolpath-common `F1`/`F2`/`I`/`M`. |
| `python utils/plot_stagewise_pipeline.py --dataset …` | Same math, executed **stage by stage**. Writes `stage0_load/` … `stage7_realization/` plus `cross_stage_attribution/`. Built to hunt jagged / unsmoothed solver profiles. |

folders (`make_plots=False`). Plots appear only on the CLI path, and only when
`--no-plots` is **not** set.

## Shared conventions (both pipelines)

**Solver vs RobotStudio.** Overlay plots use a fixed palette: **green = solver**,
**blue = RobotStudio**. Dashed green is typically raw IK (pre-spline). Do not
read the per-joint rainbow (`J1`…`J6`) as RS/solver.

**Region shading** (lettered plots A–D, A3/A4):

| Band | Meaning |
|---|---|
| Green | **cruise** — `v* ≈ v_lim` (profile is riding the ceiling) |
| Light red | **transient** — `v* < v_lim` (ramping, not at the limit) |
| Darker red | **boundary** — start/stop pads |

A vertical dashed line labelled `bottleneck Jk (vel|accel)` is the sample that
most tightly caps the profile.

**Two arc-length coordinates.** Mixing them is the most common misread.

| Symbol | Frame | Used in |
|---|---|---|
| `s` / `s_eval` / `s_act` | Path parameter of the profiler (robot-base TCP arc, or SE(3) arc if `--se3-arc-length`) | Almost all A–T plots, stagewise stages 1–7 |
| `s_pos` | Pure position arc of the flange/TCP in base | Stage 1, stage 5 governor, SE(3) conversion |
| `s_tool` / `s_plate` | Knife-tip arc in the **plate / tool** frame | Group M, frame-gain `g`, reported cut speed |

**Frame gain.** `g(s) = ds_tool / ds_base`. When the knife reorients, the flange
travels far for little cut → `g ≪ 1` (“gain needle”). Reported cut speed is
`v_tool = g · ṡ`. Joint-limit ceilings live in **path space** (`ṡ`); commanded
schedules live in **tool frame** (`v_cmd`). Group K and stages 3/5 exist to keep
those two spaces honest.

**Velocity modes.**

- `commanded` — `v* ≤ v_cmd(s)` from toolpath column 8, and joint-feasible.
- `constant` — one joint-feasible cruise (only with `--time-optimal`).
- `optimal` / `time_optimal` — joint limits only, no authored speed cap.

## Toolpath-common artifacts

These sit in `<toolpath>/`, not inside `commanded/`. Written once.

---

### `F1_input_toolpath_plate_frame.png`

**Purpose.** Sanity-check the **authored** knife-in-plate waypoints (`T_P_K`)
before any robot-base transform, blend, or TOPP. Look for the intended cut
shape, missing/duplicated WPs, and which corners the accel-transient classifier
flagged (red).

**Axes.**

- If the path is nearly planar: **X [mm]** vs **Y [mm]** (equal aspect).
- Otherwise a 3D plot: **X, Y, Z [mm]**.
- Blue arrows = tool **Z** (falls back to tool **X** if Z is out of plane).
- Green dots = steady WPs; red triangles = accel-transient WPs; lime = start.
- Steelblue polyline = steady segments; red polyline = segments touching a
  transient WP.

**Why it is in the pipeline.** All later speed numbers are “along this cut.”
If F1 is the wrong geometry, every RS comparison is meaningless. Transient
coloring tells you which programmed corners will be **excluded from the
cruise benchmark** (group G).

**Notes.** Written only if it does not already exist (`F1.exists()`), so a
re-run into the same folder will not overwrite it.

---

### `F2_waypoints_robot_base_frame.png`

**Purpose.** Same waypoints after the Zund knife → robot-base transform
(`T_B_P`). This is the frame IK, the quintic spline, and TOPP actually run in.

**Axes.** Same as F1, but coordinates are robot-base millimetres.

**Why it is in the pipeline.** Confirms the knife calibration is applied
(path should sit at the expected height/offset vs F1). A flipped or
untransformed cloud here produces bogus `dq/ds`, gain needles, and FK residuals.

**Notes.** Same transient coloring as F1 (WP *i* is the same physical point).

---

### `orientation_smooth_compare.png` (+ `orientation_smooth.json`)

Written at the toolpath folder when Step-5b orientation smoothing ran
(`smooth_orientation=True`, default). Absent from a run if smoothing was
skipped.

**Purpose.** Before/after of piecewise-SLERP vs smoothed `R(s)` **on the base
arc** `s`. Complements group M (which replots the same idea on the **tool**
arc). Look for: small geodesic residual but large `dθ/ds` / `d²θ/ds²` change
→ smoothing **redistributed phasing**, it did not change the pose.

**Axes** (4 stacked panels, x = arc-length `s` [mm]):

| Panel | Y |
|---|---|
| 1 | Cumulative geodesic angle `θ_cum` [deg] — raw SLERP vs smooth |
| 2 | `dθ/ds` [deg/mm] |
| 3 | `d²θ/ds²` [deg/mm²] — raw shows WP-rate kinks |
| 4 | Geodesic residual `|Δθ|` [deg] between smooth and raw samples |

If raw SLERP is unavailable, only the three smooth-spectrum panels are drawn.

**Why it is in the pipeline.** Unsmoothed SLERP puts C0 kinks in orientation
rate at every waypoint. Those kinks become `d²q/ds²` spikes → `v_accel`
notches → sawtooth in `v*` (see group J). This plot is the first check that
Step 5b did (or did not) remove them.

## Group A — `A_geometry_spline/`

Validates that the **quintic LSQ spline** is a faithful, differentiable
stand-in for raw IK `q(s)`. Every later ceiling (`v_vel`, `v_accel`) is
built from `q'(s)` and `q''(s)`. If A is wrong, B–E are fiction.

Shared x-axis: **arc-length `s` [mm]**. Six stacked joints J1–J6.

---

### `A1_geometry_spline_validation.png`

**Purpose.** Overlay raw IK vs spline `q(s)`, optionally vs RobotStudio joints.
Look for: spline tracking raw IK; RS tracking the same configuration (no
branch flip); binding-joint shading lining up with later bottlenecks.

**Axes.** Y = joint angle **q [deg]**.

- Dashed = IK raw samples (`s_raw`).
- Solid = quintic spline on the eval grid.
- Blue (when RS is present) = recorded RS joints.
- Blue/orange vertical bands on a joint = that joint binds via **velocity** /
  **acceleration**.
- Green/red background = cruise/transient/boundary.

**Why it is in the pipeline.** TOPP never sees the raw IK polyline; it sees
this spline. A configuration mismatch vs RS here (especially J4–J6 wrap) will
show up as huge G2/G3 errors that are **not** speed-profile bugs.

**Notes.** Angles are unwrapped only later in G2. A1 can look discontinuous at
±180° even when the spline is fine.

---

### `A2_residual_per_joint.png`

**Purpose.** Fit quality: `spline(s_raw) − q_raw` per joint. Grey band is
`±0.2 deg` (`_RESID_TOL_DEG`). Red dots = samples outside the band.

**Axes.** Y = **residual [deg]**.

**Why it is in the pipeline.** A spline that undershoots a sharp IK corner
will **invent curvature** (`q''` too small or too large) and silently change
`v_accel`. Residuals clustered at blend zones or orientation corners are the
usual smoking gun. This is a **validation** plot, not a performance plot.

---

### `A3_dqds_per_joint.png`

**Purpose.** Geometric joint rate `dq/ds` — how fast each joint must move per
millimetre of path. Solid = quintic; dashed = finite difference on raw IK;
blue = RS estimate `q̇ / ṡ` (only where `|ṡ|` is large enough).

**Axes.** Y = **dq/ds [deg/mm]**. Zero line drawn.

**Why it is in the pipeline.** This is the **velocity ceiling** ingredient:
`v_vel,j = q̇_max,j / |dq_j/ds|`. Peaks in `|dq/ds|` are where that joint
will cap TCP speed. Comparing spline vs raw vs RS tells you whether a
needle is (a) real geometry, (b) spline ringing, or (c) RS noise.

**Notes.** If SE(3) arc-length is on, spline derivatives are chain-ruled back
to the **position** arc so the three curves are commensurable. Binding-fraction
text (`vel-bind X% | accel-bind Y%`) is per joint.

---

### `A4_d2qds2_per_joint.png`

**Purpose.** Geometric joint curvature `d²q/ds²`. Same overlay style as A3.
RS uses `(q̈ − c·s̈) / ṡ²`.

**Axes.** Y = **d²q/ds² [deg/mm²]**.

**Why it is in the pipeline.** This is the **acceleration ceiling** ingredient:
`v_accel,j ≈ sqrt(q̈_max,j / |d²q_j/ds²|)`. WP-rate spikes here become the
sawtooth in `v_lim` (group J). If A4 is noisy and H2/`orientation_smooth`
is not, the curvature is coming from **joints**, not orientation SLERP.

## Group B — `B_velocity_limits/`

---

### `B_velocity_limit_curve.png`

Three stacked panels. This is the **MVC (maximum velocity curve)** the TOPP
integrator is allowed to touch.

**Purpose.** Answer “what is capping TCP speed at this `s`?” Look at B1 first
(which envelope is lowest), then B3 (kind + joint).

**Axes.** X = `s` [mm].

**B1 — what caps TCP speed?** Y = speed [mm/s].

| Curve | Meaning |
|---|---|
| Black `v_lim` | Combined ceiling actually used by TOPP |
| Grey dashed `v_lim_joint` | Joint-only ceiling **before** `v_cmd` (commanded mode) |
| Blue `v_vel` | Envelope of per-joint velocity ceilings |
| Orange `v_accel` | Joint-accel ceiling (clipped for display) |
| Purple `v_secant` | Accel cap from raw-path secant (not the spline) |
| Dotted purple `v_cmd(s)` | Toolpath column-8 schedule (commanded mode) |

**B2 — per-joint velocity ceilings.** Y = `q̇_max / |dq/ds|` [mm/s]. Six
colored joints + black `v_vel` envelope. The lowest joint at each `s` is the
velocity binder.

**B3 — binding strips.** Two heat strips:

- Top: **which joint** (tab10 colors J1–J6).
- Bottom: **kind** — blue = velocity, red = acceleration.

**Why it is in the pipeline.** This is the **constraint construction** step.
A dip in `v*` that already exists in `v_lim` is not a TOPP bug. A dip that
appears only in `v*` (group C/D) is an integration / start-stop issue.

**Notes.** `v_secant` exists because spline `q''` can understate curvature at
undersampled corners. If B1’s orange and purple disagree, the spline is
smoothing over a real accel limit (see J3).

## Group C — `C_path_dynamics/`

---

### `C_path_parameter_dynamics.png`

**Purpose.** The TOPP **phase-plane** view: how the realized profile sits
under the ceiling, plus tangential acceleration. Look for: `v*` riding
`v_lim` on cruise (green bands); `s̈ ≈ 0` on cruise; saturated `s̈` on
ramps; RS overlay agreeing in shape.

**Axes.** X = `s` [mm].

| Panel | Y | What to look for |
|---|---|---|
| **C1** | `v*` [mm/s] (tool-frame cut speed when `frame=tool`) plus `v_lim` and RS `ṡ` | Solver should sit on `v_lim` in green bands |
| **C2** | `u = ṡ²` [mm²/s²] vs `v_lim²` | Touch = cruise; below = transient. This is the variable Heun actually integrates |
| **C3** | `s̈` or `dv_tool/dt` [mm/s²] | ≈ 0 on cruise; bang-bang on accel/brake. RS from Savitzky–Golay `d(speed)/dt` |

**Why it is in the pipeline.** Confirms TOPP did its job **given** `v_lim`.
If C1 rides a jagged ceiling, the ceiling (B/J) is the bug, not Heun. If C1
is smooth under a jagged ceiling, smoothing/governor is hiding geometry.

## Group D — `D_optimal_profile/`

---

### `D1_optimal_vs_ceiling.png`

**Purpose.** Single-axis “did we violate the ceiling?” plot. Red dots =
`v* > v_lim` (should be empty aside from numerical crumbs).

**Axes.** X = `s` [mm], Y = speed [mm/s]. Dashed black = `v_lim`, solid green
= `v*`. Region shading + bottleneck marker.

**Why it is in the pipeline.** Feasibility check of the integrator. A red
cloud means the TOPP step or the `v_cmd` cap construction is broken.

---

### `D2_joint_velocity_time.png`

**Purpose.** Realized joint velocities vs **time**, against ±`q̇_max`. Blue
shading = intervals where **this joint** is the velocity binder. Red dots =
≥ 95% of the limit.

**Axes.**

- Six upper panels: X = **time t [s]**, Y = **q̇ [deg/s]**, dashed = ± joint
  velocity limit. Text: “binds X% of path.”
- Bottom strip: TCP **x, y, z [mm]** vs time, dual axis **v\* [mm/s]**, with
  the bottleneck instant marked.

**Why it is in the pipeline.** Path-space plots hide duration. Time-domain
saturation shows whether a short geometric spike actually used the motor
budget. The bottom TCP strip lets you match a joint spike to a physical
location on the cut.

---

### `D3_joint_acceleration_time.png`

**Purpose.** Same layout as D2 for **q̈**. Orange shading = this joint binds
via **acceleration**.

**Axes.** Y = **q̈ [deg/s²]** vs **t [s]**; dashed = ±`q̈_max`. Bottom TCP/`v*`
strip identical to D2.

**Why it is in the pipeline.** Accel-bound corners are where `v_accel` /
`v_secant` notches live. If D3 never touches the dashed limits but `v*` still
dips, the dip is **commanded** (`v_cmd` / governor / RS zone), not joints.

## Group E — `E_constraint_utilization/`

---

### `E_constraint_utilization_heatmap.png`

**Purpose.** Compact view of how close every joint is to **either** its
velocity or acceleration limit along the path.

**Axes.** X = `s` [mm], Y = joints J1–J6, color = `max(|q̇|/q̇max, |q̈|/q̈max)`

zoom. Not a substitute for B3 (B3 is which constraint **constructed** `v_lim`;

## Group G — `G_robotstudio_compare/`

**Benchmarking** against a matched RobotStudio recording. Skipped if no RS CSV
was found. Speeds are unified to the **tool frame**.

Also writes `rs_path_derivatives.csv` (RS `ṡ`, `s̈`, `dq/ds`, `d²q/ds²`) and
`G_rs_compare_summary.txt`.

Shaded exclusion spans (transient / RS-zone lookup / `v_cmd` ramp) are **not**
scored. Fail marks are `|v* − v_RS| > 10%` of RS **and** `> 2.5 mm/s` on
non-excluded samples.

---

### `G1_tcp_speed_accel_vs_rs.png`

**Purpose.** Primary RS speed/accel overlay, plus (commanded mode) a
per-waypoint lollipop of `|v_solver − v_RS|`.

**Axes.**

| Panel | X | Y |
|---|---|---|
| Speed | `s` [mm] | TCP cut speed [mm/s] — RS, solver `v*`, `v_lim`, `v_cmd(s)` |
| Accel | `s` [mm] | `|TCP accel|` [mm/s²] — RS CSV `linear_accel`, RS `|d(speed)/dt|`, solver `|dv_tool/dt|` |
| Jerk (only with `--jerk`) | `s` [mm] | `|TCP jerk|` [mm/s³] — S–G `d/dt` of accel |
| **G1c** (commanded) | WP index | `|v_solver − v_RS|` [mm/s] at each programmed WP |

G1c: green lollipops pass, red fail, grey × ignored (transient / lookup).
Dashed line = absolute tolerance (default 2.5 mm/s).

**Why it is in the pipeline.** This is the **Experiment-24 cruise benchmark**.
Read G1c for a pass/fail per corner; read the speed panel for shape (needles,
phase lag, overshoot). Accel disagreement at corners is expected if RS
filters more heavily than the solver.

**Notes.** Red circles on the speed panel are dense-sample fails, not WP
fails. Exclusion shading must be respected — scoring a blend/accel-transient
region as a cruise fail is a false alarm.

---

### `G2_joint_position_vs_rs.png`

**Purpose.** Configuration tracking: did the robot follow the same `q(s)`?

**Axes.** 2×3 joints. X = `s` [mm], Y = **q [deg]**. RS unwrapped. Green =
solver spline, blue = RS.

**Why it is in the pipeline.** A speed match with a joint mismatch means
different IK branches or a frame error. Debug **geometry/IK** before TOPP.

---

### `G3_joint_velocity_vs_rs.png`

**Purpose.** Realized `q̇(s)` vs RS and vs ± velocity limits (dashed).

**Axes.** Y = **q̇ [deg/s]**.

**Why it is in the pipeline.** Joint-velocity **validation**. Solver should
not exceed dashed limits. RS may look noisier (logged at ~24 ms). A joint
that saturates in G3 but not D2 is an `s` vs `t` sampling effect — trust D2
for time-domain saturation.

---

### `G4_joint_acceleration_vs_rs.png`

**Purpose.** Same as G3 for **q̈**, dashed = ± accel limits.

**Axes.** Y = **q̈ [deg/s²]**.

**Why it is in the pipeline.** Accel-limit validation. RS accel is
differentiated from a coarse log — spikes in blue that are absent in green
are often log noise, not a solver miss.

---

### `G5_joint_jerk_vs_rs.png` (optional, `--jerk`)

**Purpose.** Savitzky–Golay `d/dt` of joint acceleration (~80 ms window).

**Axes.** Y = **q⃛ [deg/s³]**. No joint-jerk limits drawn.

**Why it is in the pipeline.** Optional smoothness diagnostic. High solver
jerk with low RS jerk usually means the profiler is more aggressive than the

## Group H — `H_tcp_rotation/`

---

### `H_tcp_rotation.png`

**Purpose.** TCP **orientation dynamics** along the path: how much the tool
reorients (`θ`), the geometric rate (`dθ/ds`), and the **realized** angular
speed/accel for this mode’s `ṡ(t)`. Red bands = accel transients.

**Axes.** X = `s` [mm].

| Panel | Y | Notes |
|---|---|---|
| **H1** | `θ` [deg] | Cumulative geodesic angle of dense pose quaternions (LSQ-smoothed) |
| **H2** | `dθ/ds` [deg/mm] | Geometric — property of the toolpath, independent of speed mode |
| **H3** | `ω = (dθ/ds)·ṡ` [deg/s] | Realized angular speed. Blue = RS `orientation_speed` (frame-invariant) |
| **H4** | `α = dω/dt` [deg/s²] | `θ''·ṡ² + θ'·s̈` (analytic, no FD) |

**Why it is in the pipeline.** Separates “the path asks for a lot of rotation”
(H2) from “this speed profile realizes a lot of ω” (H3). Commanded vs
optimal will share H1/H2 and differ in H3/H4. **Warning:** H2 is spline-smoothed
and can **hide** piecewise-SLERP kinks — use group J raw FD for that.

## Group J — `J_sawtooth_debug/`

Upstream dump for **WP-rate notches** in `v*` / `v_lim`. H can hide them; J
plots **raw** Feature-3 quaternion finite differences, programmed WP spacing,
and which ceiling formula binds each notch.

Also writes `sawtooth_upstream.csv`, `waypoint_spacing_along_s.csv`,
`raw_orientation_fd.csv`, `summary.txt`.

---

### `J1_waypoint_spacing_vs_notches.png`

**Purpose.** Test the hypothesis “notches sit on programmed waypoints.”

**Axes.** X = `s` [mm].

| Panel | Y |
|---|---|
| **J1a** | `v*` and `v_lim` [mm/s]; crimson triangles = detected `v_lim` notches; grey ticks = WP locations |
| **J1b** | `Δs` between consecutive WPs [mm] |
| **J1c** | Notch-to-notch gap [mm] vs local `ΔWP` at each notch; title shows correlation |

**Why it is in the pipeline.** High corr(notch gap, `ΔWP`) means **waypoint
spacing is in the causal chain** (SLERP / blend / secant window interacting
with WP rate). Low corr means look at geometry (orientation pile-up, see M)
instead of spacing.

---

### `J2_raw_orientation_vs_joint_curvature.png`

**Purpose.** Compare **raw** orientation FD to H’s smoothed spline, then to
joint-path curvature `κ = max_j |d²q/ds²|` (the quantity that feeds `v_accel`).

**Axes.** X = `s` [mm] (raw grid for ori, eval grid for `κ`). WP ticks.

| Panel | Y |
|---|---|
| **J2a** | `θ` [deg] — raw dense quats vs H spline |
| **J2b** | `dθ/ds` [deg/mm] — raw FD vs H2 |
| **J2c** | `d²θ/ds²` [deg/mm²] — WP-rate spikes in RAW ⇒ orientation is upstream |
| **J2d** | `κ` [deg/mm²], y clipped to mid-path p99.5 so the start singularity does not squash the axis |

**Why it is in the pipeline.** If RAW `d²θ/ds²` spikes at WP rate but H is
smooth, **piecewise-SLERP is the geometric root** and Step 5b / blend timing
is the fix — not TOPP. If `κ` carries the same cadence, those spikes are
already inside the accel ceiling.

---

### `J2e_ori_vs_joint_curvature_zoom.png`

**Purpose.** Dedicated overlay of RAW `|d²θ/ds²|` vs joint `κ`, with peak
count vs `n_WP` in the title (`ori_peaks / n_WP ≈ 1` supports one kink per
waypoint).

**Axes.** Two panels, both Y = [deg/mm²], X = `s` [mm].

**Why it is in the pipeline.** J2’s four panels compress the y-scale. J2e is
the one to screenshot when arguing “orientation curvature cadence matches
joint κ cadence.”

### `J3_ceiling_binder_attribution.png`

**Purpose.** Name **which formula** put the notch into `v_lim`.

**Axes.**

| Panel | Content |
|---|---|
| **J3a** | `v_vel`, `v_accel`, `v_secant`, `v_lim`, optional `v_capped` (RS lookup) [mm/s]; notch markers |
| **J3b** | Color strip: blue=`v_vel`, orange=`v_accel`, purple=`v_secant`, grey=other/tie |

**Why it is in the pipeline.** Majority binder in J3c tells you which

## Group K — `K_base_frame_command/`

Only when `res.frame == "tool"` and `plate_gain` is present.

---

### `K_base_frame_command.png`

**Purpose.** Show the **command conversion** `v_cmd(tool) → ṡ_target(path)`
that TOPP actually tracks, plus the gain and base-frame twist that explain
why they differ.

**Axes.** X = `s` [mm].

| Panel | Y |
|---|---|
| 1 | Path speed [mm/s]: converted ZOH target, pointwise `v_cmd/g`, achieved `ṡ`, joint ceiling in path space |

# Part 2 — `utils/plot_stagewise_pipeline.py`

Same core functions and defaults as the test harness, but each pipeline stage
is executed explicitly. Every intermediate is dumped to CSV **and** plotted
at full resolution. Programmed-waypoint / segment boundaries are grey
vertical lines (`_mark_edges`). A red `rough=…` annotation is RMS second
difference (texture magnitude) — the jaggedness metric.

Layout:

```text
<out>/<case>/<mode>/
  stage0_load/
  stage1_parameterize/
  stage2_splines/
  stage3_frame_gain/
  stage4_ceilings/
  stage5_command_target/
  stage6_topp/
  stage7_realization/
<out>/<case>/
  cross_stage_attribution/     # commanded mode only
```

`--time-optimal` repeats stages 0–7 under `constant/` and `optimal/`.

**`s_act` vs `s_pos`.** The solver integrates in the **active** parameter
`s_act`. With SE(3) off, `s_act = s_pos`. With `--se3-arc-length`, `s_act`
includes `λ·Δθ` and is sampled uniformly; `s_pos` is then non-uniform on
purpose.

## Suggested reading order

**“Does commanded speed match RobotStudio in cruise?”**
`tcp_velocity_profile` → G1 (including G1c) → transient mask → K / stage 5
if the miss is a needle.

**“Why is there a needle / stall at this cut location?”**
M6 → M2 → M5 → M4/M3 → K panel 2 → B1/J3. If M says geometry, stop; do not
retune TOPP.

**“Why is the profile jagged?”**
`cross_stage_attribution` panel 2–3 → stage2 `dqds` vs stage6 `ṡ` → J2/J3
if curvature cadence matches WPs → A2/I if the spline is the liar.

**“Is the spline even a valid path?”**
